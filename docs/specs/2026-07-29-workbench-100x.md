# Workbench 100x — Agentic Audit

**Status:** Proposal, awaiting selection
**Date:** 2026-07-29
**Scope:** Every surface of the workbench module — what to keep, what to cut, what to add, so the shell reads as a supervision console for agents rather than a well-built VS Code clone.
**Method:** Read-only pass over `frontend/src/store/layout/`, `frontend/src/components/layout/`, `frontend/src/commands/`, `store/activity.ts`, `store/focusMode.ts`, `store/terminalWatch.ts`, the agent and git surfaces, `frontend/design-system/MASTER.md`, all twenty-two docs in `docs/features/`, the three prior briefs in `.claude/prompts/`, and the last sixty commits. No source file was modified.

---

## Thesis

The workbench is not underbuilt — it is built for the wrong protagonist. Every organising decision in it assumes a human with one pair of eyes on one worktree: tab state is keyed by worktree by design (`store/layout/state.ts`), escalation stops at the status bar of the *active* worktree (`store/activity.ts:escalate`), focus modes exist to remove chrome so one person can concentrate (`store/focusMode.ts`), and the agent is a slide-over chat whose thread is memory-only "deliberately" (`commands/agent.ts:24`). That was correct when the user was authoring. It is wrong the moment three agents are working in three worktrees and the user's job is deciding which one to look at.

The good news is that the hard part is already built and is pointed the right way. `store/activity.ts` is a closed signal vocabulary with a *pure* escalation function whose entire purpose is "a user must never have to open a pane to learn something happened in it" (MASTER §7.5.3 rule 1). `components/layout/statusSegments.ts` is a priority registry whose stated design rationale is that "the further from the user's current focus the fact is, the more important it is that the bar keeps showing it." `components/layout/freshness.ts` makes "how old is this number" mechanical. Those three modules are, almost word for word, a supervision substrate. They were built for terminals and git counts and then never pointed at the workload that actually needs them.

So this audit's central finding is not "add an agent panel." It is that **the escalation chain has a hole and a dead end**, and both are cheap to fix:

- **The dead end.** `failed` is the only signal in the §7.5.3 vocabulary that survives focus — it clears on explicit acknowledgement only (`activity.ts:acknowledgeTab`). It is the signal designed for unattended work. Nothing in the codebase can raise it. `noteFinished(id, false)` has no caller, because `pty-exit` is emitted with a unit payload at `src-tauri/src/lib.rs:271` and the exit code never reaches the frontend. `store/terminalWatch.ts:18` documents this in a nine-line comment and defers it. The most important signal in the system is unreachable for want of about thirty lines of Rust.
- **The hole.** `escalate()` models three levels of zoom — tab, group header, status bar — and its `EscalationInput` has no worktree axis at all. A signal raised in a worktree the user is not currently in escalates *nowhere*. Today that is a minor gap because the user switched away from that worktree deliberately. With agents it is the primary case: the whole point is that work continues where you are not looking. Rule 1 is violated by construction, one level above where anyone has looked.

Everything else in this document is downstream of those two. The ranked list favours items that make existing primitives do the job they were designed for over items that add new systems beside them.

One framing correction to the brief that commissioned this: "next-generation agentic development workbench" implies additions. The three most valuable moves here are a thirty-line Rust change, a fourth level on an existing pure function, and cutting an embedded web browser that is holding the entire Tauri dependency at an exact pin.

## Part 1 — Surface by surface

Each surface: what it costs, what it earns under three-concurrent-agent supervision, and what it would be if designed for that session from scratch.

### 1. Workspace rail — `components/layout/WorkspaceRail.tsx` (416 lines)

**Costs** ~212px of permanent horizontal space (`PANEL_BOUNDS`, `store/layout/prefs.ts:61`), nine chords (`workspace.select.1…9`), a persisted width and collapse state, drag-reorder and inline rename logic held in component-local signals (`WorkspaceRail.tsx:34-44`).

**Earns** the only always-visible list of every worktree in play. Under supervision this is the single most valuable rectangle on screen — and it is currently spending it on names and `git worktree list` badges.

**Would be** the supervision board. Every row already corresponds one-to-one with a place an agent can be working. A row wants: the worktree's aggregate activity mark, ahead/behind with a freshness state (`freshness.ts` already computes it), and a dirty count. The rail is the natural fourth level of the escalation chain, and it is already always on screen except under zen.

**Verdict: Keep, and make it the escalation target (A3).**

### 2. Pane split tree — `store/layout/panes.ts` (438 lines), `components/layout/MainSurface.tsx` (1150 lines)

**Costs** a recursive tree model, a four-group cap, drop-zone geometry (`paneDrop.ts`), 31 tests, and the two-layer render (strips + measuring boxes below, panes absolutely positioned above) that exists so a cross-group drag does not remount an xterm or a child webview.

**Earns** side-by-side. The two-layer render decision is correct and load-bearing — it should survive every proposal here.

**Would be** unchanged in shape. The cap and the tab-group axis are already covered by the in-flight `workbench-layout-grouping` prompt; this audit does not re-propose them. One observation the grouping prompt does not cover: `resolveGroupTabs`'s "empty first group claims everything" default (`panes.ts:104`) means a split layout has *no* concept of a group being dedicated to a worktree other than the active one. Cross-worktree splitting is structurally impossible today. That is a deliberate scoping decision, not a bug, but it is the reason A4's review queue must be a tab kind rather than a pane mode.

**Verdict: Keep as-is.**

### 3. Tab strip — `components/layout/TabStrip.tsx` (1061 lines), `store/layout/tabs.ts` (721 lines)

**Costs** the largest component in the module, ten `TabKindSpec` entries, six localStorage keys, pins, preview tabs, a closed-tab LIFO, drag payload and insertion carets.

**Earns** everything a tab strip earns. The registry refactor was right: a kind costs one spec entry.

**Would be** nine kinds, not ten (see cuts C1 and C2), plus an eleventh that matters — `agent` (A1). The strip's real weakness under supervision is that every tab is a *place*, and an agent run is an *event with a lifetime*. A run has states the tab vocabulary already has words for (running → finished/failed) and the strip already reserves the slot to show them.

**Verdict: Keep. Add one kind, cut two.**

### 4. Activity and escalation — `store/activity.ts` (233 lines)

**Costs** a module-level store, a `visible` set published by `MainSurface`, a pure `escalate()` and its tests.

**Earns** the correct model, tested, with the right rules written down. `setVisibleTabs` suppressing `finished` for work the user watched happen, and refusing to clear `failed` on focus, are both exactly right.

**Would be** four levels instead of three, and would have a reachable `failed`. Also worth noting: the signal set (`bell | running | finished | failed | dirty | stale`) is genuinely sufficient for agents — an agent run is running, then finished or failed. It needs no new dot, which is what §7.5.3 rule "do not invent a new dot" wants to hear. **The vocabulary is not the gap. The reach is.**

**Verdict: Keep the model. Fix the reach (A2, A3).**

### 5. Status bar — `components/layout/StatusBar.tsx` (625), `statusSegments.ts`

**Costs** nine resting priorities, an overflow popover, measured widths.

**Earns** the last stop for a signal from a pane you cannot see, and the only chrome zen keeps.

**Would be** the same registry with two changes: `backgroundActivity` (priority 100) should distinguish "in a group you cannot see" from "in a worktree you are not in", because those need different click targets; and two segments are not paying rent (see C3, C4).

**Verdict: Keep. Prune two segments, split the top one.**

### 6. Command palette, file finder, switchers — `commands/CommandPalette.tsx`, `QuickPick.tsx`, `fuzzy.ts`, `FileFinder.tsx`, `TabSwitcher.tsx`, `WorktreeSwitcher.tsx`

**Costs** one shared overlay chrome, one fuzzy scorer, four consumers, a recently-used action float.

**Earns** the consolidation was correct — one box, one highlight, four uses.

**Would be** extensible. `commands/registry.ts` (172 lines) builds a static array. There is no way for a non-app source to contribute an action. Under supervision the palette is the natural place to type "restack the auth branch" and have it dispatched to a run. That needs an action *source* interface, not a bigger array.

**Verdict: Keep. Add a source interface (A6).**

### 7. Keymap and bindings — `commands/keymap.ts`, `keys.ts`, `keybindings.ts`, `actionIds.ts`

**Costs** one declarative table, a capture-phase listener, a three-value scope model (`global | outside-terminal | outside-text-surfaces`), ~75 action ids.

**Earns** derived accelerator labels that cannot drift — genuinely one of the best decisions in the codebase.

**Would be** slightly smaller. There are now four tab-navigation models bound to chords simultaneously: document order (`tab.next`/`tab.prev`), MRU (`tab.mru-next`/`prev`), jump-to-N (`tab.select.1…9`), and back/forward (`ui.navigate-back`/`forward`). Three is defensible; four is a keymap that grew by accretion (C5).

**Verdict: Keep. Reclaim two chords.**

### 8. Snapshots and session restore — `commands/snapshots.ts`, `components/layout/SnapshotManager.tsx`

**Costs** a versioned v2 format with read-time migration, content-key addressing, a manager dialog, two palette actions.

**Earns** a restore that survives regenerated tab ids — the content-key decision is right.

**Would be** unchanged, except that it now has a neighbour it will be confused with: the in-flight grouping prompt's layout presets. The distinction (snapshot = contents, preset = arrangement) must be stated in `docs/features/snapshots.md` or users will learn it by losing something.

**Verdict: Keep. Document the boundary.**

### 9. Terminal sidebar and PTY watch — `components/layout/TerminalSidebar.tsx`, `store/terminalWatch.ts`, `components/terminal/TerminalPane.tsx`

**Costs** a 1500ms `processInfo` poll per shell, refcounted; a sidebar tab; a terminal tab kind.

**Earns** the refcounted move out of `TabStrip` was exactly right, and for the stated reason: "a signal that only exists while someone is looking at the surface it would appear on is not a signal."

**Would be** the host for agent runs. Agents run in shells. `terminalWatch` already detects the busy→idle edge, which is 90% of "the agent finished." What it cannot see is *how* it finished — the pty-exit gap (A2). It also polls, which at three agents × 1500ms is fine but is the wrong shape for a run that should report its own transitions.

**Verdict: Keep. Close the exit-code gap (A2) — highest leverage-per-line in this document.**

### 10. Git sidebar — `components/git/GitSidebar.tsx`, `changesNav.ts`

**Costs** 320px, seven reorderable sections, a virtualized changes list, the freshness contract on the header.

**Earns** the review surface. `changesNav.ts` is a pure keyboard-nav reducer over three lists treated as one surface — the single most reusable thing in the git module and the obvious substrate for a review queue.

**Would be** worktree-plural. Every number in it is scoped to the active worktree; under supervision the question is "which of my four worktrees has changes waiting on me", and no surface answers it.

**Verdict: Keep. Generalise `changesNav.ts` for A4.**

### 11. Editor window — `components/editor/` (48 files)

**Costs** its own window (or stacked view), editor groups, LSP process management in `src-tauri/src/lsp/`, breadcrumbs, find-in-files, external change detection.

**Earns** a real editor. Configuration breadth is covered by the in-flight `editor-config-parity` prompt and is not re-proposed.

**Would be** differently cadenced in exactly one place. `externalChanges.ts` detects changes by batched stat **on window focus and on git ref change** — a deliberate choice made to avoid an OS handle per file, and correct when the only other writer was `git checkout`. With an agent writing files continuously in the background, "on focus" means the editor is stale for the entire period you are watching it happen. This is a freshness-contract violation (§7.5.4) that did not exist when the decision was made (A8).

**Verdict: Keep. Revisit the detection cadence.**

### 12. Agent panel — `components/agent/AgentPanel.tsx` (254 lines), `commands/agent.ts` (222 lines)

**Costs** a right-edge slide-over, one chord (`agent.toggle`), a BYO-CLI adapter shared with commit drafting, an in-memory thread per worktree.

**Earns** the `AuditItem` trail — every turn records which repo state fed it — is the most forward-looking thing in the codebase and nothing else is built on it.

**Would be** unrecognisable. Today the agent is a chat box that happens to know about the repo. Three specific problems:
- **A slide-over is a modal shape for a background activity.** It covers the surface you would watch the agent's effects on, and it holds exactly one conversation at a time — for one worktree, in a product whose organising unit is the worktree.
- **The thread is memory-only "deliberately — the agent is a scratch surface, not a persisted document"** (`agent.ts:23`). That reasoning was sound for a question-and-answer box. It is wrong for a run whose output you review after a restart. This audit argues against that comment explicitly (A9).
- **`busy` is a single global boolean** (`agent.ts:26`). The data model cannot represent two agents running at once, which is the workload.

**Verdict: Cut the shape, keep the grounding. This is the surface that most needs redesign (A1).**

### 13. Settings and empty states — `components/settings/SettingsDialog.tsx`, `components/layout/emptyStates.ts`

**Costs** a 1972-line dialog (addressed by the config prompt); a registry with a test asserting no two empty states share an icon or sentence.

**Earns** the empty-state registry's test is a small, excellent idea — it is the property that decides whether ten empty states are usable or ten grey shrugs.

**Verdict: Keep both. No change proposed here.**

### 14. Focus modes — `store/focusMode.ts` (57 lines)

**Costs** two chords, two module-level signals, a render filter in `MainSurface`, a status segment at priority 90.

**Earns** zen and maximize as render filters over an untouched tree — "restores the exact prior geometry" true by construction. Elegant, and 57 lines.

**Would be** the same, with one caveat that is already handled: zen forces every signal to the status bar because there are no strips (`activity.ts:escalate`, the `input.zen` branch). Correct. If A3 lands, zen must also keep the rail's aggregate mark reachable or it becomes a place where worktree-level signals disappear — the same trap zen was careful to avoid for group-level ones.

**Verdict: Keep. Add the A3 interaction to its contract.**

## Keep

Unchanged, and load-bearing for everything below: the two-layer pane render (`MainSurface.tsx`); the pure-reducer discipline in `panes.ts` / `navigation.ts` / `changesNav.ts` / `statusSegments.ts` / `escalate()`; the derived accelerator labels in `keymap.ts`; content-key snapshot addressing (`snapshots.ts`); the empty-state uniqueness test (`emptyStates.test.ts`); the refcounted PTY watch (`terminalWatch.ts`); focus modes as render filters (`focusMode.ts`); the `AuditItem` grounding trail (`commands/agent.ts`).

Five, each with the file and the reason. Cuts are proposals; nothing is removed by this document.

### Where these argue with MASTER.md

- **A3 extends §7.5.3 rule 1's escalation chain from three levels to four** (tab → group header → status bar → *worktree row*). The rule's text names three because three were what existed; its stated principle — "a user must never have to open a pane to discover something happened in it" — demands the fourth the moment work happens in a worktree you are not in. MASTER §7.5.3 should be amended, not worked around.
- **A1 adds no new dot**, which §7.5.3 explicitly forbids. An agent run is `running`, then `finished` or `failed` — the existing vocabulary is sufficient, and that is a point in the model's favour.
- **A9 contradicts an in-code design comment** rather than a MASTER rule. Stated openly above rather than quietly reversed.
- **A7 refines §7.5.5** from a per-event choice to a rate-aware one. The section's own principle ("pick the lowest level that will actually be seen") already implies this; it just never had to reason about concurrency.

Nothing was dropped from this list for being small or awkward. The two items that came closest to being cut are recorded above the table with their reasons (`ui.swap-sidebars`, collapsing `preview` into `file`).

### Build these three first

**A2, then A3, then A1** — in that order, and the order is the argument.

A2 is thirty lines of Rust that make the most important signal in the design system reachable for the first time. It has no dependencies, no design risk, and its absence is already documented as a known gap in a nine-line comment nobody has acted on. Doing it first also means A1 inherits a working finished/failed path rather than building a parallel one.

A3 closes a rule-1 violation that exists *today* — it is not an agentic feature, it is a bug in the escalation model that agents make unignorable. `escalate()` is pure and tested, so the change is additive and cheap to verify. It also converts the rail from a navigation list into the supervision board every other proposal here wants to hang things on.

A1 is the large one and should be third, not first, because both of its substrates (a reachable `failed`, a worktree-level escalation target) are what make it worth building. Landing A1 first would mean an agent-run tab kind whose failure state cannot be raised and whose signal escalates nowhere once you switch worktrees — which is the product the audit is trying to get away from.

C1 (cutting the browser) is ranked fourth and deliberately not in the three: it is the highest-value *removal* in the document and it needs a product decision, not an engineering one.

### Ruled out on capability

Nothing was ruled out as unbuildable. One item carries an unresolved capability question: **A8** depends on a filesystem watcher, and context7's Tauri 2 documentation did not surface a v2 `tauri-plugin-fs` watch API either way. The fallback (`notify` as a direct `src-tauri` dependency) is known-good, so A8 is buildable regardless — but check the already-present `tauri-plugin-fs` 2.5 before adding a crate.

Two proposals are assumed-landed dependencies and were not re-proposed: workbench layout grouping (named tab groups, layout presets, raising the group cap, auto-grouping) and VS Code-level editor configuration (settings schema, search, per-language overrides, JSON view).
